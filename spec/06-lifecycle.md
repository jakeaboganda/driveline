# 6. Driveline Component Model (DCM) & Lifecycle

The **Driveline Component Model (DCM)** is a C-ABI ([§9](09-abi.md)). Native components export the `dl_*` entry points. Components packaged as `.fmu` files export only standard FMI 3.0 functions, and the runtime drives them as [§7](07-fmu-packaging.md) describes.

## 6.1 Component Lifecycle State Machine

```text
                 ┌──────────────────────┐
                 │  1. Uninstantiated   │◄───────────────────────────┐
                 └──────────┬───────────┘                            │
                            │ dl_instantiate                         │
                            ▼                                        │
                 ┌──────────────────────┐                            │
                 │   2. Instantiated    │ dl_set_parameters          │
                 └──────────┬───────────┘                            │
                            │ dl_configure_structure                 │
                            ▼                                        │
                 ┌──────────────────────┐                            │
                 │ 3. StructuralConfig  │ dl_set_parameters          │
                 └──────────┬───────────┘                            │
             t = 0          │          t > 0                         │
           ┌────────────────┴────────────────┐                       │
           │ dl_enter_cold_init              │ dl_enter_warm_start   │
           ▼                                 ▼                       │
┌──────────────────────┐          ┌──────────────────────┐           │
│   4a. ColdInitMode   │          │  4b. WarmStartMode   │◄──────┐   │
└──────────┬───────────┘          └──────────┬───────────┘       │   │
           └────────────────┬────────────────┘                   │   │
                            │ dl_exit_init_mode                  │   │
                            ▼                                    │   │
                 ┌──────────────────────┐     re-trim:           │   │
                 │     5. StepMode      │────────────────────────┘   │
                 └──────────┬───────────┘     dl_enter_warm_start    │
                            │ dl_do_step repeats in StepMode         │
                            │ dl_terminate                           │
                            ▼                                        │
                 ┌──────────────────────┐                            │
                 │    6. Terminated     │────────────────────────────┘
                 └──────────────────────┘     dl_free_instance
```

**Allowed Calls:** This table is the complete list of legal calls. The diagram above omits some `dl_free_instance` edges, and the table governs. Any other call returns `DL_STATUS_ERR_STATE` and leaves the state unchanged. `dl_free_instance` returns nothing, so the runtime never calls it outside the states the table allows. A call that returns an error also leaves the state unchanged.

| Function | Allowed In | Next State |
| :--- | :--- | :--- |
| `dl_instantiate` | Uninstantiated | Instantiated |
| `dl_set_parameters` | Instantiated, StructuralConfig | unchanged |
| `dl_configure_structure` | Instantiated | StructuralConfig |
| `dl_enter_cold_init` | StructuralConfig, at $t = 0$ only | ColdInitMode |
| `dl_enter_warm_start` | StructuralConfig at $t > 0$ (splice), or StepMode (re-trim) | WarmStartMode |
| `dl_exit_init_mode` | ColdInitMode, WarmStartMode | StepMode |
| `dl_do_step` | StepMode | StepMode |
| `dl_terminate` | Instantiated, StructuralConfig, ColdInitMode, WarmStartMode, StepMode | Terminated |
| `dl_free_instance` | every state except Uninstantiated | Uninstantiated; the handle becomes invalid |

## 6.2 Detailed Lifecycle Transition Rules

1. **`Instantiated` (`dl_instantiate`, `dl_set_parameters`):** `dl_instantiate` verifies `abi_version` and stores the host map callback table (`dl_host_map_callbacks_t`) and its `host_ctx`. The runtime then passes every component parameter from the DSL (for example `kp: 1.8` or `reaction_delay: 0.18s`) through `dl_set_parameters`, by name, in SI units, with `Time` in nanoseconds ([§15.4](15-manifest.md)). `dl_set_parameters` is valid in `Instantiated` and `StructuralConfig`. An unknown name or a wrong type returns `DL_STATUS_ERR_INVALID_ARG`.
2. **`StructuralConfig` (`dl_configure_structure`):** Passes the input port count, the per-port ring buffer capacities `port_history_depths[]`, and the number of actors that the instance serves (`max_actors`): 1 for a per-actor instance and $M$ for a group instance ([§10](10-composition.md)). Multi-input components such as `BoschPCS_v4` get one depth per port, for example $N_0 = 8$ and $N_1 = 5$. Non-buffer ports have depth $0$.
3. **`ColdInitMode` (`dl_enter_cold_init` at $t = 0$), Coupled Trim Protocol:**
   Before Pass 1, the runtime visits every component instance in Phase 2 order ([§11](11-execution.md)), with each actor's or group's physics instances after its Stage 2 instances and per-actor physics instances in `bind` order, and calls `dl_instantiate`, `dl_set_parameters`, and `dl_configure_structure` on it before it moves to the next instance. It then initializes the pipeline in three passes. Each pass covers all actors and groups in the Phase 2 order of [§11](11-execution.md): ascending `actor_id`, with a group sorted by its smallest member, and components in topological order.
   * **Pass 1 (Host Steady State & Tick 0 Sensor Projection):**
     1. For each actor, the host calls `frenet_to_world` at the spawn `(road_id, lane_id, s_0, d_0)`. The returned `psi_lane` and `kappa_lane` are the lane's heading and signed curvature in the direction of increasing $s$, with positive curvature turning left. Let $\sigma$ be the spawn lane's direction sign ([§2](02-conventions.md)). The travel direction is $\psi_{\text{travel}} = $ `psi_lane` for $\sigma = +1$ and `psi_lane` $+ \pi$, wrapped to $(-\pi, \pi]$, for $\sigma = -1$. The curvature of the actor's path, the curve at offset $d_0$ along the direction of travel, is $\kappa_0 = \sigma \cdot$ `kappa_lane` $/ (1 - $ `kappa_lane` $\cdot d_0)$. A spawn with `kappa_lane` $\cdot d_0 \ge 1$ lies at or beyond the center of curvature and is `DL_STATUS_ERR_NUMERIC`. The factor $\sigma$ holds because a curve that turns left toward increasing $s$ turns right toward decreasing $s$. The runtime also computes the road grade $\theta_{\text{road}}$ and bank $\phi_{\text{road}}$ at the spawn point ([§2](02-conventions.md)).
     2. It sets $\dot{\psi}_0 = v_0 \kappa_0$ and solves the steady state of [§8](08-steady-state.md) for the tier of the actor's physics component. That solve gives $v_{\text{lat,ra}}$, $\delta_{\text{ss}}$, and $\beta_{\text{cg}}$. The spawn heading is $\psi_0 = \psi_{\text{travel}} - \operatorname{atan2}(v_{\text{lat,ra}}, v_0)$, wrapped to $(-\pi, \pi]$, so the rear-axle velocity is tangent to the lane and the actor follows it. For `KS`, or at $v_0 = 0$, $\psi_0 = \psi_{\text{travel}}$.
     3. If Tier 1 is populated, it computes static axle normal loads. Tier 0 has no mass, so a Tier-0-only actor skips this step and step 4:
     $$F_{z,f} = m g \cos\theta_{\text{road}}\cos\phi_{\text{road}} \frac{l_r}{L} - m g \sin\theta_{\text{road}} \frac{h_{\text{cg}}}{L}, \qquad F_{z,r} = m g \cos\theta_{\text{road}}\cos\phi_{\text{road}} \frac{l_f}{L} + m g \sin\theta_{\text{road}} \frac{h_{\text{cg}}}{L}$$
     With the [§2](02-conventions.md) sign convention, an uphill road ($\theta_{\text{road}} > 0$) moves load to the rear axle.
     4. If Tier 2 is populated, it sets `num_wheels = 4` and fills `wheels[0..3]` in the header's order: `normal_load_fz` is half of the axle load, `omega` is $v_0 / R_{\text{eff}}$, `steer_angle` is $\delta_{\text{ss}}$ at the front and 0 at the rear, `slip_angle_alpha` is the [§8](08-steady-state.md) axle slip angle ($\alpha_f$ or $\alpha_r$, 0 for `KS` or when $v_0 < 1\text{ m/s}$, every reverse speed included), `surface_mu` is $\mu$ at the contact point ([§17.1](17-standard-library.md)), and the slip ratio, suspension deflection, and suspension velocity are 0. The physics component solves its own deflection in Pass 3. `powertrain` has `gear_mode` `DRIVE` (or, at a warm start with $v_{\text{lon}} < 0$, `REVERSE` with ratio $i_R$), `active_gear_index` from the `SimpleDrivetrain` gear rule ([§17](17-standard-library.md)), `motor_or_engine_speed_rads` $= (|v_0| / R_{\text{eff}})\, i_g\, i_{\text{fd}}$ (with $i_R$ and `active_gear_index` $= -1$ in `REVERSE`), and zero torque and brake pressures. Otherwise `num_wheels = 0`, and `wheels[]` and `powertrain` are zero.
     5. It fills each actor's `dl_init_context_t`, with `struct_size` and `abi_version` as [§9.1](09-abi.md) requires, `sim_time_ns = 0`, and `is_warm_start = 0`. `chassis_state` holds `actor_id`, `timestamp_ns = 0`, the spawn pose with roll and pitch 0, $v_0$, $\dot{\psi}_0$, $v_{\text{lat,ra}}$, $a_{\text{lon}} = -v_{\text{lat,ra}} \dot{\psi}_0$, $a_{\text{lat}} = v_0 \dot{\psi}_0$ (the rear-axle acceleration on the steady circle), `front_wheel_angle` $= \delta_{\text{ss}}$, $\beta_{\text{cg}}$, and the spawn `road_id`, `lane_id`, $s_0$, and $d_0$ as the map cache. `chassis_state.odometer_m` is 0. `latched_intent` is `VELOCITY_TARGET` with `v_ref` $= v_0$ and `stop_at_odometer` $=$ `+INFINITY`, `LANE_OFFSET` on the spawn lane with `d_ref` $= d_0$, and `turn_signal = OFF`. `latched_kinematic_ctrl` is `ACCEL` with `a_lon_cmd` $= 0$ and `jerk_lon_cmd` $=$ `+INFINITY`, and `ANGLE` with `steer_angle_cmd` $= \delta_{\text{ss}}$ and `steer_rate_cmd` $=$ `+INFINITY`. `latched_actuator_ctrl` is `PEDALS` with `throttle` $= 0$ and `brake` $= 0$, `ANGLE` with `steering_wheel_norm` $= \operatorname{clamp}(\delta_{\text{ss}} / \delta_{\max}, \pm 1)$, and `DRIVE` with `manual_gear_index = 0`. Every latched frame states every group in its baseline mode ([§5](05-checkpoints.md)), carries the actor's `actor_id` and `timestamp_ns = 0`, and has no `NONE` group.
     6. After steps 1 to 5 have run for every actor, it runs sensor projection at $t = 0$ once over the complete spawn World. This projection is Tick 0's Phase 1. Tick 0 does not run Phase 1 again, so no buffer holds two samples at $t = 0$.
   * **Pass 2 (Stage 1 and Stage 2 Cold Init):** Stage 1 and Stage 2 components enter `dl_enter_cold_init` and then `dl_exit_init_mode`, one instance at a time in Phase 2 order, each finishing both calls before the next begins. Pass 3 does the same for physics, and a splice processes a multi-component replacement the same way. Stage 1 components initialize freely, because their output comes from perception. Each Stage 2 component sets its internal state, such as integrators and filters, so that its first output reproduces the steering of the latched frame of its output type, or of `T` for an `Override<T>` output. A `Lon<T>` component reproduces the longitudinal fields instead, and a `Lat<KinematicControlFrame>` component reproduces the steering. Longitudinal pedal trim for steady speed (drag and rolling resistance) is the job of the component that produces `ActuatorControlFrame`. Initialization returns no output, so the runtime checks the trim on Tick 0: after the first `dl_do_step` of each Stage 2 component whose output type is not `Lon<T>`, it compares the output's road-wheel steering angle with the latched one, and for an `Override<T>` output with the latched frame of `T`. A `Lon<T>` output carries no steering and is not checked, and neither is an output, or a latched frame, whose steering group is not in `ANGLE` mode. For `ActuatorControlFrame`, the road-wheel angle is `steering_wheel_norm` $\cdot \, \delta_{\max}$. If the two differ by more than $10^{-3}\text{ rad}$, the runtime reports `DL_STATUS_WARN_TRIM_MISMATCH` ([§14](14-diagnostics.md)) and continues. For a group instance the check and any report are per served actor.
   * **Pass 3 (Stage 3 Physics Trim):** Physics components enter `dl_enter_cold_init`, solve their internal states at the Pass 1 steady state, and then leave through `dl_exit_init_mode`. Internal states include suspension deflection $z_{i,0}$ and tire relaxation. Physics does not re-solve $\delta$. If the Tick 0 check reports no `DL_STATUS_WARN_TRIM_MISMATCH`, Tick 0 starts at the linear-tire steady state of [§8](08-steady-state.md). Otherwise the first ticks contain a transient.
4. **`WarmStartMode` (`dl_enter_warm_start` at $t > 0$), Fidelity Promotion & Demotion:**
   * **Tier Change:** A splice that replaces the actor's physics component, through `physics_model` or through a chain that contains it, is a promotion if the outgoing component's `required_tier` is 0 and the incoming one's is 1 or 2, and a demotion in the reverse case. Tiers 1 and 2 share the `ST` steady state of [§8](08-steady-state.md), so a splice between them changes no field.
   * **Promotion, Tier 0 (`KS`) $\rightarrow$ Tier 1/2 (`ST` / `MB`):** The runtime keeps the position, the rear-axle course angle $\chi = \psi + \gamma$, $v_{\text{lon}}$, and $\dot{\psi}$, where $\gamma = \arctan(v_{\text{lat,ra}} / v_{\text{lon}})$ for $v_{\text{lon}} \ne 0$ and $\gamma = 0$ otherwise. A tier change keeps the sign of $v_{\text{lon}}$, so keeping $\chi$ keeps the path in reverse too. It solves the `ST` steady state of [§8](08-steady-state.md) at $(v_{\text{lon}}, \dot{\psi})$ and passes it to the incoming physics component. Five fields change: $v_{\text{lat,ra}}$ goes from $0$ to the solved value, $a_{\text{lon}}$ becomes $a_{\text{lon}} - v_{\text{lat,ra}} \dot{\psi}$ so that $\dot{v}_{\text{lon}}$ is kept ([§5.3](05-checkpoints.md)), `front_wheel_angle` goes from $\delta_{\text{KS}}$ to $\delta_{\text{ss}}$, $\beta_{\text{cg}}$ follows from both, and the yaw becomes $\psi = \chi - \gamma$, wrapped to $(-\pi, \pi]$, so the actor keeps its path, as at spawn. With linear tires, the lateral force and yaw moment of the incoming model are balanced at the first step if the upstream steering command reproduces $\delta_{\text{ss}}$, that is, if the re-trim reports no `DL_STATUS_WARN_TRIM_MISMATCH`.
   * **Demotion, Tier 1/2 $\rightarrow$ Tier 0:** The runtime keeps the position, $\chi$, $v_{\text{lon}}$, and $\dot{\psi}$. It sets $v_{\text{lat,ra}} = 0$, `front_wheel_angle` $= \delta_{\text{KS}}$ from [§8](08-steady-state.md), and $\psi = \chi$ wrapped to $(-\pi, \pi]$, and $a_{\text{lon}}$ becomes $a_{\text{lon}} + v_{\text{lat,ra}} \dot{\psi}$ with the old $v_{\text{lat,ra}}$ so that $\dot{v}_{\text{lon}}$ is kept. It also sets $a_{\text{lat}} = v_{\text{lon}}\dot{\psi}$, as the kinematic model reports. These five fields and $\beta_{\text{cg}}$ change.
   * **Committed State Update:** For a promotion or demotion, the runtime writes the changed fields into the committed state $X(t)$ before any warm start. The map cache is left unchanged. The incoming physics component, the re-trim set, the next tick's sensors, `own_state`, and `actor.state` all see the updated state.
   * **Re-Trim of Upstream Controllers:** A promotion or demotion can change `front_wheel_angle`. In the same inter-tick window, the runtime moves the **re-trim set**, in Phase 2 order, from `StepMode` through `dl_enter_warm_start` and `dl_exit_init_mode` back to `StepMode`, each instance finishing both calls before the next begins: every Stage 2 instance with a data path to the new physics component, that serves the actor and whose output type is not `Lon<T>`. Stage 2 arbiters are included. Stage 1 arbiters are not. Components outside the set keep running unchanged. It passes the latched frames defined below. Each re-trimmed component sets its internal state so that its next output reproduces the new steering angle, to the extent its design allows. Until that next scheduled step, its consumers keep receiving its last output, with the steering replaced as described below for each actor whose tier changed. A stateless component, such as `StanleyLat`, computes its output from its inputs alone. A Mode B FMU cannot be re-trimmed at all ([§7](07-fmu-packaging.md)). The runtime does not call it, keeps delivering its last output with the steering replaced as below until its next scheduled step, and reports `DL_STATUS_WARN_TRIM_MISMATCH`. The runtime checks the first output of each re-trimmed component other than a Mode B FMU, and of each Stage 2 component created by a splice, the way it checks Tick 0 in Pass 2, and reports `DL_STATUS_WARN_TRIM_MISMATCH` if the steering angles differ by more than $10^{-3}\text{ rad}$. For a re-trim, the check covers only the actors whose physics tier changed, against their updated latched steering.
   * **Latched Frames at $t > 0$:** The **committed baseline frame** of a type is the frame that the rules of Pass 1 step 5 build from the committed state, stamped with the next tick's time $t$, with `a_lon_cmd` equal to the committed $\dot{v}_{\text{lon}} = a_{\text{lon}} + v_{\text{lat}}\dot{\psi}$, $v_0 = \max(v_{\text{lon}}, 0)$, $d_0 = $ `frenet_d`, $\delta_{\text{ss}} = $ `front_wheel_angle`, the committed `road_id` and `lane_id` in place of the spawn lane, and, if $v_{\text{lon}} < 0$, `gear_mode = REVERSE`. At $t > 0$, the runtime first replaces each group of a latched `KinematicControlFrame` or `ActuatorControlFrame` that is not in its baseline mode, and is not `NONE`, with that group of the committed baseline frame. A converted frame keeps its `timestamp_ns`, and it is the latched frame in every later use: the context, the output before the first step, and a re-formed merged frame. For a re-trim, the latched frame of each type is the last frame of that type that left the component, or, if none left it, the last frame of that type that reached its input. For a splice, the same rule applies to the outgoing target as a whole, and for a type that only flowed inside the target it is the last frame on the edge of that type nearest the target's output, and among edges equally near, the one whose producer comes last in Phase 2 order ([§11](11-execution.md)). In these rules a `Lon<T>` or `Lat<T>` output counts as the merged frame at its `+`, and an `Override<T>` output or input never counts. A latched frame taken from a `Lon<T>` or `Lat<T>` edge that reaches no `+` has each `NONE` group replaced by that group of the committed baseline frame, and keeps its `timestamp_ns`. Every output that reaches an Arbiter's `secondary`, whatever its declared type, counts as an `Override<T>` output here and before its first step. A component whose input and output types are equal, such as `JerkLimiter`, therefore gets its own last output. Every component of the replacement gets these frames, and a replacement that has not stepped yet passes on the latched frames it was given. For a type that these rules do not cover, the latched frame is the committed baseline frame, even if frames of that type flowed elsewhere for the actor. The chassis state is the committed state.
   * **Output Before the First Step:** Until a replacement first steps, its consumers receive its latched frame of its output type, converted to that output type:
     * A full `T` output delivers the latched frame unchanged, a trajectory included, except to a `Lon<T>` or `Lat<T>` port, which receives it as the next item describes.
     * A `Lon<T>` or `Lat<T>` output, or a full output at such a port, delivers it with the unstated groups `NONE` and their fields zero. A latched `IntentFrame` in `SPATIOTEMPORAL_TRAJECTORY` is first replaced by the committed baseline frame.
     * An `Override<T>` output delivers a frame with every group `NONE` and every other field zero, carrying the served actor's `actor_id` and stamped with the next tick's time, which is 0 at cold init.
   * **Steering After a Tier Change:** For an actor whose physics tier changes in the window, the runtime sets the steering group to the new `front_wheel_angle` in every warm-start context, whether a splice or a re-trim, in the last output of every re-trimmed or replaced producer that has not stepped since, and in the current merged frame of every `+` that such a producer feeds. In a `KinematicControlFrame` the steering group becomes `ANGLE` with `steer_angle_cmd` $= $ `front_wheel_angle` and `steer_rate_cmd` $=$ `+INFINITY`. In an `ActuatorControlFrame` it becomes `ANGLE` with `steering_wheel_norm` $= \operatorname{clamp}($`front_wheel_angle` $/\, \delta_{\max}, \pm 1)$. A `NONE` steering group stays `NONE`. The runtime then zeroes every field that the new modes do not use, and each frame keeps its `timestamp_ns`. Longitudinal fields keep their last values, so longitudinal control continues without a step.
   * **Warm-Start Context:** A warm-start context is built like a cold-init one, from the committed state at the tick time $t$ of the next tick: `sim_time_ns` $= t$, `is_warm_start = 1`, `chassis_state` is the committed state, and `wheels[]` and `powertrain` follow Pass 1 steps 3 and 4 with $v_0 = v_{\text{lon}}$, the current `front_wheel_angle`, and the grade and bank at the current pose, except that no steady state is solved. Each axle's `slip_angle_alpha` comes from the committed state by the `DynamicSingleTrack` formulas of [§17.5](17-standard-library.md), and is 0 when $v_{\text{lon}} < 1\text{ m/s}$, every reverse speed included, as in [§8](08-steady-state.md). The latched frames follow the rule above.
   * **Contexts per Actor:** `dl_enter_cold_init` and `dl_enter_warm_start` take one `dl_init_context_t` per actor, and the component matches each context to its actor slot by `chassis_state.actor_id`. An instance gets contexts only for the actors that it serves, in its `actor_ids` order. Cold init and a splice pass one for each of them. A re-trim passes contexts only for the served actors whose physics tier changed, and the component keeps the state of every other actor.
   * **Size of the Change:** For linear tires, $\delta_{\text{ss}} - \delta_{\text{KS}} \approx K_{\text{us}}\, v_{\text{lon}} \dot{\psi}$, where $K_{\text{us}} = \frac{m}{L}\left(\frac{l_r}{C_{\alpha f}} - \frac{l_f}{C_{\alpha r}}\right)$ is the understeer gradient. [§8](08-steady-state.md) gives a test vector.
